# Автоматичне підтвердження оплати на картку monobank у Telegram-боті

Telegram-бот, який сам бачить звичайний переказ на картку чи рахунок ФОП у monobank і підтверджує замовлення — без еквайрингу, без скриншотів чеків і без менеджера. Node.js 20+, **без залежностей**, з тестами.

> **EN:** A dependency-free Node.js example of a Telegram bot that confirms plain card transfers to a monobank account automatically, using the Monobank personal webhook and a unique kopeck amount per order. Article in Ukrainian below; code comments are in English.

---

## Задача

Малий бізнес часто приймає оплату фразою «скиньте на картку», а потім хтось звіряє скриншоти. Еквайринг (LiqPay, WayForPay, еквайринг monobank) вирішує це, але потребує договору й бере комісію з кожного платежу.

Monobank Personal API дає власнику рахунку дві потрібні речі: виписку і **вебхук**, який надсилає кожну нову транзакцію. Цього достатньо, щоб бот сам зрозумів: прийшла саме ця оплата.

## Як це працює

```
Клієнт: /buy
Бот:    «Переказ рівно 100.37 грн на картку …»        ← createPendingOrder(): унікальна сума
Клієнт: переказує 100.37 грн
monobank → POST /mono-webhook?key=…  {amount: 10037}  ← handleMonoWebhook()
Бот:    «Оплату 100.37 грн отримано»                  ← popPendingOrder(): GETDEL
```

### 1. Вебхук, а не опитування виписки

Виписку персонального API можна запитувати не частіше одного разу на хвилину, тож клієнт чекав би підтвердження до хвилини. Вебхук реєструється один раз ([scripts/register-webhook.js](scripts/register-webhook.js)) і приходить одразу після транзакції.

Дві деталі:

- **Перевірочний запит.** Одразу після реєстрації monobank звертається до вашого URL. Якщо сервер не відповість `200`, вебхук не зареєструється. Тому все, що не схоже на надходження, отримує `200` і ігнорується.
- **Секрет в URL.** Персональний вебхук нічим не підписаний: будь-хто, хто знає адресу, може надіслати «оплату». URL містить випадковий `?key=…`, який сервер перевіряє (через `timingSafeEqual`). Сам `MONO_TOKEN` запущеному боту не потрібен — лише скрипту реєстрації.

### 2. Платіж ідентифікується сумою з точністю до копійки

Коментар до переказу ненадійний: його не пишуть, пишуть не те, а частина способів переказу його не передає. Тому кожне відкрите замовлення отримує **унікальну суму**: ціна плюс 0–99 копійок. Замовлення на 100 грн стає 100.37 грн, і вебхук знаходить його саме за цією сумою.

```js
// src/orders.js
export async function createPendingOrder(store, priceUAH, order) {
  const baseKopecks = Math.round(priceUAH * 100);
  for (let attempt = 0; attempt < MAX_OFFSET_KOPECKS; attempt++) {
    const seq = await store.incr("order:seq");
    const amountKopecks = baseKopecks + (seq % MAX_OFFSET_KOPECKS);
    if (await store.setNX(`order:${amountKopecks}`, order, ORDER_TTL_SECONDS)) return amountKopecks;
  }
  return null; // усі 100 сум біля цієї ціни зайняті
}
```

- **Лічильник, а не випадкове число:** сусідні замовлення отримують різні копійки, тож колізій майже немає навіть без повторних спроб.
- **`SET NX` як замок:** два одночасні замовлення не можуть отримати одну суму.
- **TTL:** незаплачене замовлення саме звільняє суму, копійки не «закінчуються».
- **Чесна межа:** до 100 відкритих замовлень на одну ціну одночасно. Якщо більше — функція повертає `null`, і бот просить спробувати пізніше, а не видає дубль.

### 3. Підтвердження рівно один раз

```js
// src/webhook.js (скорочено)
if (allowedAccounts.length && !allowedAccounts.includes(body.data.account)) return { status: 200 };
const order = await popPendingOrder(store, item.amount); // GETDEL — атомарно
```

- **`GETDEL`, а не `GET` + `DEL`:** якщо monobank доставить ту саму транзакцію двічі, лише перша доставка отримає замовлення.
- **Фільтр рахунку:** вебхук приходить по *всіх* рахунках власника токена. Без перевірки `account` випадковий переказ на іншу картку з тією самою сумою підтвердив би чуже замовлення.
- **Завжди `200`:** помилку обробки логуємо, але не повертаємо, щоб не отримати серію повторних доставок.

## Запуск

Потрібні Node.js 20.6+ і публічна HTTPS-адреса для вебхука (на сервері або тимчасово через тунель на кшталт ngrok чи cloudflared).

```bash
git clone <цей репозиторій> && cd monobank-telegram-payments
cp .env.example .env          # заповніть TELEGRAM_BOT_TOKEN, MONO_WEBHOOK_SECRET, MONO_TOKEN, CARD_NUMBER
npm test                      # 4 тести, без мережі
npm start                     # бот (long polling) + вебхук на :3000/mono-webhook
npm run register-webhook -- https://your-public-url   # покаже id рахунків і зареєструє вебхук
```

Впишіть id рахунку магазину з виводу `register-webhook` у `MONO_ACCOUNT_ID` і перезапустіть. Далі: `/buy` у боті → переказ точної суми → підтвердження в чаті.

Особистий токен monobank дає доступ до виписки всіх ваших рахунків — зберігайте його лише в `.env` і не комітьте.

### Сховище

За замовчуванням стан зберігається в пам'яті процесу — цього досить для одного сервера й тестів. Для serverless (Vercel, Netlify) або кількох інстансів задайте `UPSTASH_REDIS_REST_URL` і `UPSTASH_REDIS_REST_TOKEN`: тоді `SET NX` і `GETDEL` виконуються в Redis, і різні інстанси не видадуть однакову суму.

## Чого цей підхід не вміє

- **Це не еквайринг.** Клієнт робить звичайний переказ. Повернення коштів, оплата карткою будь-якого банку в один клік, Apple Pay / Google Pay — це до LiqPay, WayForPay чи еквайрингу monobank.
- **Сума має збігтися до копійки.** Якщо клієнт округлив, автопідтвердження не буде; замовлення лишиться відкритим до кінця TTL, і його доведеться підтвердити вручну.
- **Облік і податки.** Надходження на особисту картку для бізнесу — питання до бухгалтера. Технічно приклад так само працює з рахунком ФОП.

Для невеликих обсягів це найпростіший старт: без договорів і комісії платіжного сервісу, з підтвердженням за секунди. Коли оплат стане багато, логіку замовлень можна залишити й перейти на еквайринг.
